# Benchmarks

Three scripts, each comparing every scheduling policy on an identical, seeded workload:

- `bench/run.sh`: 8 identical simulated replicas (32k-token KV cache, batch 16, 4000 tok/s prefill, 40 tok/s decode) plus a cloud-mode provider for spillover, on a shared-context chat workload. Writes `results.md`.
- `bench/hetero.sh`: same, but replicas 7 and 8 have half the capacity. Writes `results-hetero.md`.
- `bench/agents.sh`: agent sessions (prompts that grow turn by turn, with think time between turns) mixed with one-off RAG requests, on replicas with half the KV cache, so the caches are under pressure. Writes `results-agents.md`.

```bash
bench/run.sh                                   # ~2 minutes
BENCH_SEEDS="1 2 3" bench/agents.sh            # averaged over three seeds
BENCH_DURATION=300s BENCH_RPS=12 bench/run.sh  # longer, hotter
POLICIES="prefix_aware pack" bench/hetero.sh
```

Env knobs: `BENCH_RPS` (default 7; 2.5 in `agents.sh`), `BENCH_DURATION` (120s simulated), `BENCH_SEEDS` (results are averaged across seeds), `TIME_SCALE` (0.05: everything runs 20x faster than real time), `SIM_KV` (KV tokens per replica), `POLICIES`, `GATEWAY_PORT` (18080), `SIM_BASE` (19000), `CLOUD_PORT` (19101), `EXTRA_CONFIG` (extra YAML lines for the gateway, e.g. `pack_slack_blocks: 16`). The scripts refuse to start if those ports already answer.

Each run also saves per-request samples (`results/<tag>-<policy>-<seed>.samples.jsonl`), the gateway's decision log with per-candidate costs (`.decisions.json`) and its counters (`.metrics`).

## Workload

Generated by `internal/workload` (replayable with `loadgen -record/-replay`):

- 3 tenants with weights 3/2/1 and cloud budgets $2 / $1 / $0
- classes: short chat (~200 chars), RAG (8–16k chars), long (32k chars), and agent sessions (an arrival starts a session of ~5 turns; each turn's prompt is the previous prompt plus the reply and a ~1.5k-char tool result, sent an exponentially distributed think time after the previous turn completes); 64–128 completion tokens
- 30 system prompts (~1.5–4.5k chars each) with Zipf(1.1) popularity, so prefix reuse is realistic
- criticality: 70% standard, 20% sheddable, 10% critical
- open-loop Poisson arrivals at `BENCH_RPS`

Mean prompt is ~3.6k tokens; the long class alone is ~8.7k tokens, so four of them fill a replica's KV cache.

## Capacity estimate (why rps defaults to 5)

Decode alone would allow ~1.9 req/s per replica (at a full batch of 16, `40 / (1 + 0.15 × 15) ≈ 12.3` tok/s per sequence, ~102 completion tokens per request), but KV admission is the real limit: a 32k-token cache with ~3.6k tokens per request (8.7k for the long class) holds 4–9 sequences, and a request occupies its slot for prefill plus 3–7 s of decode. Measured with this workload, eight replicas serve about 4.8 req/s with zero shedding; at 10 rps more than half the requests shed. 5 rps keeps the replicas busy enough that routing decisions matter without tipping everything into overload. Raise `BENCH_RPS` to 7–8 to see saturation handling (shedding, spillover) engage.

## Reading the table

Latencies are reported in simulated milliseconds (wall time divided by `TIME_SCALE`). `p99 agent TTFT` is the tail for agent turns only. `goodput %` is the share of all requests (including shed ones) answered with a first token within 2 s. `cache hit %` is the share of prompt blocks the replicas themselves reported as prefix-cache hits, which is the number that matters; the gateway's own prediction and its error are in the JSON. `spill %` is the share served by the cloud provider; `shed %` is 503s. Per-backend shares, shed rate by criticality and TTFT percentiles by class are in the JSON reports under `results/`.
