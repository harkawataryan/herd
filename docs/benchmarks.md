# Benchmark methodology

## Setup

- 8 simulated replicas (`cmd/simbackend`): 32,768-token KV cache (16,384 in the agents run), batch of 16, prefill 4,000 tok/s, decode 40 tok/s for a single sequence degrading by 15% per extra sequence in the batch, prefix cache as large as the KV cache (freed blocks stay cached until reclaimed, as in vLLM).
- One cloud-mode provider: unbounded capacity, TTFT ~ N(600 ms, 150 ms), priced $0.15 / $0.60 per million prompt / completion tokens, available to tenants with budget.
- Everything runs at `time-scale 0.05`: one simulated second takes 50 ms of wall clock, including arrival intervals, so a 120-second trace takes 6 seconds per policy. Latencies in the tables are simulated milliseconds (wall time / 0.05).
- Gateway scrapes replica metrics every 50 ms wall (1 simulated second).

## Workload (default)

Generated by `internal/workload` from a seed, so every policy replays the identical trace:

- 20 system prompts of ~20,000 characters (~5,000 tokens) with Zipf(1.1) popularity. This is the shared-context shape: a RAG context, a long tool list, or few-shot examples reused across many conversations.
- Each request is one system prompt plus a unique user turn: 70% short (~200 chars), 30% with extra retrieved context (8–16k chars).
- 64–128 completion tokens.
- Three tenants with weights 3/2/1 and budgets $2 / $1 / $0; criticality 70% standard, 20% sheddable, 10% critical.
- Open-loop Poisson arrivals at 7 req/s, about 85% of the measured capacity of the eight replicas on this workload.
- Every result is the mean over three seeds (`BENCH_SEEDS="1 2 3"`).

## Workload (agents, `bench/agents.sh`)

The cache-pressure case. Replicas have a 16k-token KV cache (256 blocks) and the traffic is what an agent platform sees:

- 16 system prompts of ~6,000 characters with Zipf popularity, as before.
- 40% of arrivals start an **agent session** of 3–8 turns. Each turn's prompt is the previous prompt plus the assistant's reply and a ~2,000-character tool result, so a session grows from ~25 to ~80 blocks over its life. The next turn is sent an exponentially distributed think time (mean 12 s) after the previous one completes, like a tool call or a person typing. Sessions send an `X-Session-ID` header.
- 40% of arrivals are one-off RAG requests (system prompt plus 8–16k characters of retrieved text) that will never be seen again, and 20% are short chat turns.
- 1.8 arrivals/s, which is about 5 requests/s once sessions unfold, again roughly 85% of capacity.

Between a session's turns, roughly 15 blocks/s of other prompts land on its replica, so a 256-block cache turns over in about 17 s: a conversation that pauses longer than that comes back to find its prefix evicted. The live working set of all sessions (about 65 concurrent, ~50 blocks each) is larger than the whole fleet's cache, so no router can make everything hit; the question is how well each one spends the cache it has.

## What each policy can see

| policy | signal |
|---|---|
| round_robin | nothing |
| least_queue | the gateway's own in-flight count per replica |
| kv_aware | KV-cache utilization (the larger of the scraped gauge plus tokens sent since, and the gateway's own ledger of in-flight tokens) blended with in-flight / batch |
| prefix_aware | kv_aware plus the per-replica prefix index; takes the cache hit unless the replica's load score is over 0.8 |
| llmd_style | prefix-cache score (fraction of the prompt's blocks held) weighted 3, plus queue score (rank by in-flight requests) weighted 2; highest wins. A reimplementation of the default profile documented for the llm-d inference scheduler |
| dynamo_style | blocks still to prefill plus blocks of active decode on the replica; lowest wins. A reimplementation of the cost documented for NVIDIA Dynamo's KV router |
| pack | everything above expressed in one unit, prefill blocks: blocks to prefill now + expected wait for a batch slot or KV room (from the replica's completion rate and the gateway's token ledger) + the reuse value of blocks the placement evicts and risks; lowest wins, with a few blocks of slack to keep conversations and prompt families where they are |

llmd_style and dynamo_style are written from those projects' public documentation to give Herd a fair comparison on the same workload. They are not those projects' code, and the real schedulers have options (latency prediction, session affinity, tuned weights) that the defaults don't enable.

## Reading the results

Time to first token is the headline because it is what a user feels and because it is where KV pressure shows first: a replica that has run out of KV cache queues the request internally before prefill starts. End-to-end latency is dominated by decode time, which no router can change, so the policies differ less there.

In the homogeneous run, `least_queue` already beats `round_robin` because Poisson arrivals and mixed prompt sizes leave replicas unevenly loaded at any instant. `kv_aware` improves the tail further by seeing prompt size (through KV usage) rather than request count. `prefix_aware` wins at every percentile because 82% of requests skip most of their prefill, which both lowers their own TTFT and frees the replica sooner for everyone else.

In the heterogeneous run, round-robin's p99 explodes because the two half-capacity replicas receive a full share of traffic and their internal queues grow without bound over the trace; the live policies send them about 4–5% each and keep the tail within an order of magnitude of the homogeneous case.

## Ablation: what the eviction pricing buys

`pack` has four ingredients: the token ledger, the expected-wait model, keeping conversations and families in place (the slack), and the eviction value. On the agents workload, turning the eviction value off (`evict_weight: 0.001`) and varying the slack moves the results by less than the seed-to-seed noise:

| variant | p50 | p95 | p99 | goodput | cache hit |
|---|---|---|---|---|---|
| slack 8, evict weight 1 (default) | 467 ms | 3027 ms | 5400 ms | 92.2% | 45.1% |
| slack 4, evict weight 1 | 480 ms | 2767 ms | 5440 ms | 92.8% | 45.4% |
| slack 16, evict weight 1 | 460 ms | 2807 ms | 5200 ms | 92.2% | 46.9% |
| slack 32, evict weight 1 | 487 ms | 2933 ms | 5227 ms | 92.5% | 46.5% |
| slack 8, evict weight ~0 | 473 ms | 2880 ms | 5367 ms | 91.9% | 44.6% |

(Three seeds each, from an earlier run of the same workload; absolute numbers differ slightly from the table in `results-agents.md`.) The ledger and the wait model are what separate `pack` from `prefix_aware`; an earlier version of the policy that priced evictions but used a stale KV gauge was worse than every baseline. The eviction value is kept because it is cheap, principled and never hurt, but the honest summary is that on these workloads the cache is too small for the live working set and the policy's budget is dominated by queueing, not by what gets evicted.

## Caveats

- The simulator is a model, calibrated to the qualitative shape of real servers, not to a specific GPU or model. Treat absolute milliseconds as relative. In particular it does not slow prefill down when the decode batch is busy (chunked prefill does on real servers), which flatters every policy equally.
- The gateway's prefix index is a belief about each replica's cache. The load generator compares it with what the replicas report per request (`X-Sim-Cached-Blocks`): the mean error is under two blocks on these workloads.
- Three seeds per policy. Seed-to-seed variance is larger than the gaps between the three load-aware policies on the shared-context workload, and about the size of pack's advantage on the agents workload, so read the agents table as a consistent edge rather than a large one.
- The expected-wait model needs the servers' prefill rate (`prefill_tps`) to convert seconds into blocks. The benchmark sets it from the simulator's configuration; on real hardware measure it once.
- Spillover is to a mock provider. With real keys, replace the provider URL and set `api_key_env`.
