# Benchmark methodology

## Setup

- 8 simulated replicas (`cmd/simbackend`): 32,768-token KV cache, batch of 16, prefill 4,000 tok/s, decode 40 tok/s for a single sequence degrading by 15% per extra sequence in the batch, prefix cache as large as the KV cache (freed blocks stay cached until reclaimed, as in vLLM).
- One cloud-mode provider: unbounded capacity, TTFT ~ N(600 ms, 150 ms), priced $0.15 / $0.60 per million prompt / completion tokens, available to tenants with budget.
- Everything runs at `time-scale 0.05`: one simulated second takes 50 ms of wall clock, including arrival intervals, so a 120-second trace takes 6 seconds per policy. Latencies in the tables are simulated milliseconds (wall time / 0.05).
- Gateway scrapes replica metrics every 50 ms wall (1 simulated second).

## Workload (default)

Generated by `internal/workload` from a seed, so every policy replays the identical trace:

- 20 system prompts of ~20,000 characters (~5,000 tokens) with Zipf(1.1) popularity. This is the shared-context shape: a RAG context, a long tool list, or few-shot examples reused across many conversations.
- Each request is one system prompt plus a unique user turn: 70% short (~200 chars), 30% with extra retrieved context (8–16k chars).
- 64–128 completion tokens.
- Three tenants with weights 3/2/1 and budgets $2 / $1 / $0; criticality 70% standard, 20% sheddable, 10% critical.
- Open-loop Poisson arrivals at 7 req/s, about 85% of the measured capacity of the eight replicas on this workload.

## What each policy can see

| policy | signal |
|---|---|
| round_robin | nothing |
| least_queue | the gateway's own in-flight count per replica |
| kv_aware | scraped KV-cache utilization plus tokens dispatched since the scrape, and in-flight / batch |
| prefix_aware | kv_aware plus the per-replica prefix index |

## Reading the results

Time to first token is the headline because it is what a user feels and because it is where KV pressure shows first: a replica that has run out of KV cache queues the request internally before prefill starts. End-to-end latency is dominated by decode time, which no router can change, so the policies differ less there.

In the homogeneous run, `least_queue` already beats `round_robin` because Poisson arrivals and mixed prompt sizes leave replicas unevenly loaded at any instant. `kv_aware` improves the tail further by seeing prompt size (through KV usage) rather than request count. `prefix_aware` wins at every percentile because 82% of requests skip most of their prefill, which both lowers their own TTFT and frees the replica sooner for everyone else.

In the heterogeneous run, round-robin's p99 explodes because the two half-capacity replicas receive a full share of traffic and their internal queues grow without bound over the trace; the live policies send them about 4–5% each and keep the tail within an order of magnitude of the homogeneous case.

## Caveats

- The simulator is a model, calibrated to the qualitative shape of real servers, not to a specific GPU or model. Treat absolute milliseconds as relative.
- The gateway's prefix index is a belief; the simulator reports its real hit ratio (`vllm:prefix_cache_hits_total` / `vllm:prefix_cache_queries_total`), which in the default run is 60–70% of blocks against the gateway's 82% of requests predicted as hits.
- A single run per policy with a fixed seed; variance across seeds is small on this workload but is not reported.
- Spillover is to a mock provider. With real keys, replace the provider URL and set `api_key_env`.
